## Defects found and fixed

### 1. `POST /api/v1/actions/rca/finalize` — unauthenticated, and wired to a handler with the wrong contract

`src/index.ts` L8459–L8560 (`handleRCAResolution`), L3786 (route).

Two handlers existed for this path. The **reachable** one (registered at L3786) was
`handleRCAResolution`, which:

- performed **no authentication at all** — no session, no signature, no shared key;
- read `{ ticketId, summary }`, while the only caller (`src/components/tickets/RCADocumentBlock.jsx`
  L85–L93) sends `{ rcaLogId, notes }`.

Net effect: `ticketId` was `undefined`, the lookup returned nothing, an unrelated
`rag_context_default` cache key was dropped, and the route returned `{ success: true }`.
The operator saw *"RCA document successfully finalized and locked"* for an RCA that was
never touched.

The **hardened** handler — the one that read `rcaLogId`/`notes` and checked a bearer token —
was registered ~300 lines further down at the old L3991 and was therefore unreachable dead
code.

Fix: deleted the unreachable duplicate; rewrote `handleRCAResolution` to require a real
Supabase operator session (`auth.getUser`), enforce the `rcaLogId`/`notes` contract, require
non-empty notes, update `hitl_audit_logs`, post the internal note, and invalidate the cache
key of the ticket's actual tenant.

**Proof:** `test/unauth-surface.test.js` — 4 cases. Against pre-fix `src/index.ts`:
`4 failed`.

### 2. `POST /api/v1/email/webhook` — unauthenticated write to delivery state

`src/index.ts` L2603–L2650.

Any POST with `{ message_id, event }` rewrote `ticket_messages.metadata.delivery_status`
for that message. Anyone could mark a message delivered/bounced/failed. Its sibling
`/api/onyx/email/webhook` had verified an EmailIt MAC all along.

Fix: accept the provider MAC over the raw body **or** the internal relay signature; return
`503` (not pass) when `EMAILIT_WEBHOOK_SECRET` is unbound.

**Proof:** 2 cases; both `failed` pre-fix.

### 3. `POST /api/v1/email/inbound` — signature check failed open

`src/index.ts` L2525–L2570.

The guard was `if (signature && env.EMAILIT_WEBHOOK_SECRET) { …verify… }`. Two ways to skip
verification entirely: send no `X-Emailit-Signature` header, or run with the secret unbound.
Either way an anonymous caller could inject `ticket_messages` rows and reopen tickets. The
dead `[tPart, v1Part]` parse inside the guard also computed `isValid = false` and then
immediately overwrote it — the parsed values were never used.

Fix: relay signature first; otherwise require a present signature and a bound secret,
`503` when unbound, `401` on a bad MAC.

**Proof:** 2 cases, both `failed` pre-fix.

### 4. `POST /email/daily-summary` — unauthenticated mail blast

`src/index.ts` L2659.

Called `generateAndSendExecutiveDigest(env)` with no credential at all: anyone could trigger
the executive digest mail from `@axim.io` as often as they liked. Now requires the internal
relay signature or `X-Axim-Network-Key`.

**Proof:** 1 case, `failed` pre-fix.

### 5. Frontend `npm test` was reporting the edge worker's coverage as its own

`vite.config.js` had no `test.include`, so vitest's default glob swept
`onyx-edge-worker/test/**` into the frontend run. `npm test` reported **17 files / 124
tests**, and exactly one of those files (`test_onyx_panel.test.jsx`, 4 tests) exercised
frontend code. The other 16 files / 120 tests were the edge worker's suites, already run by
the `edge-worker` CI job — so the `frontend` job looked covered while the React app had
essentially none.

Fix: explicit `test.include` scoped to `src/**` and root-level specs, with
`onyx-edge-worker/**` excluded; `environment: 'node'` by default with component tests opting
into `happy-dom` via docblock; `env: { NODE_ENV: 'test' }` so React resolves its development
build even in a shell that exports `NODE_ENV=production` (without it every `render()` throws
`act(...) is not supported in production builds of React`).

Added the first real frontend tests: `src/components/tickets/SLABadge.test.jsx` (7),
`src/lib/sanitize.test.js` (5), `src/lib/edgeWorkerUrl.test.js` (4).

**Before → after:** 17 files / 124 tests (16 files of worker tests) →
**4 files / 20 tests, all frontend.**

### 6. `handleStaleTicketSweep` was an empty function on the 15-minute cron

`src/index.ts` L343.

`scheduled()` fired it 96 times a day and it returned immediately. Implemented: reads
`stale_sweep_minutes` from `STATUS_KV` prefs (default 60), selects `open` tickets past the
cutoff, writes one `ticket_stale_sweep` event per ticket, returns the count.

**Proof:** 3 cases in `test/unauth-surface.test.js`, including that a `stale_sweep_minutes:
15` preference produces a 15-minute cutoff rather than the 60-minute default.

### 7. `validateAttachment` always returned `{ valid: true }`

`src/index.ts` L299.

The reject branch at the intake call site (L5160) was unreachable, so any file type or size
was accepted and base64-inlined into the request. Implemented a 5 MB cap and a
`image/png | image/jpeg | application/pdf` allow-list, matching what
`/api/v1/chat/upload-auth` already enforced.

### 8. Intake attachment encoding threw `RangeError` on large files

`src/index.ts` L326 (`bytesToBase64`), called at L5190.

`btoa(String.fromCharCode(...new Uint8Array(buffer)))` spreads every byte as a function
argument. Measured in this environment:

```
$ node -e "const b=new Uint8Array(1024*1024).fill(65); try{btoa(String.fromCharCode(...b))}catch(e){console.log(e.constructor.name,'-',e.message)}"
RangeError - Maximum call stack size exceeded
```

A legal 1 MB attachment returned 500. Replaced with a 32 KiB chunked encoder.
`bytesToBase64(new Uint8Array(1024*1024).fill(65)).length` → `1398104`
(`Math.ceil(1048576/3)*4`), which is the expected base64 length.

### 9. Two dead duplicate route registrations removed

- `POST /api/v1/tickets/callback` was registered twice (L3137 and L3444). The second was
  unreachable and was a stale copy with fewer validations — no `ticketId` guard, no PR
  metadata, no `gitops_patch_received` telemetry.
- `POST /api/v1/actions/rca/finalize` was registered twice (see defect 1).

Both unreachable copies deleted. `grep -c` for each path is now 1.

### 10. Two pairs of migrations shared a version prefix

`supabase/migrations/` had:

```
20260901000000_add_is_curated_to_telemetry.sql
20260901000000_team_profiles.sql
20261001000000_egress_webhook.sql
20261001000000_egress_webhook_tables.sql
```

Supabase keys `supabase_migrations.schema_migrations` on the version prefix, so the second
file in each pair is silently never applied — `team_profiles` would not exist, and
`getUser`-based role sync writes to it from `/api/v1/auth/sso/exchange`. Neither table has a
cross-file dependency, so renumbering is safe:

- `20260901000000_team_profiles.sql` → `20260901000001_team_profiles.sql`
- `20261001000000_egress_webhook_tables.sql` → `20261001000001_egress_webhook_tables.sql`

`ls supabase/migrations | awk -F_ '{print $1}' | sort | uniq -d` now returns nothing.
No file referenced either old name.

### 11. `wrangler.toml` shipped placeholder KV namespace ids

`onyx-edge-worker/wrangler.toml`.

```toml
[[kv_namespaces]]
binding = "STATUS_KV"
id = "fake-status-kv-id-for-now"
```

`wrangler deploy --dry-run` only validates the *shape* of a namespace id, so CI stayed green
while a real deploy would fail or ship a worker whose `STATUS_KV`/`HITL_KV` reads threw.
`STATUS_KV` backs email preferences, the diagnostics cache and rate-limit counters;
`HITL_KV` backs the 24h HITL approve/deny tokens, so emailed approval links could not be
written. Replaced both with explicit `REPLACE_WITH_…_NAMESPACE_ID` markers plus the
`wrangler kv namespace create` command, and added `test/wrangler-config.test.js` (3 tests) so
a `fake-`/`placeholder` id fails the suite instead of passing a dry run.

The adjacent cron comment claimed `0 3 * * *` was "10:00 AM UTC … before 5 AM CST"; it is
03:00 UTC (21:00/22:00 the previous evening in Central). Corrected.

### 12. Self-inflicted: body read before signature verification on `/api/v1/email/webhook`

Found while writing the test for defect 2. The first revision of the fix did
`const rawBody = await request.text()` and *then* called `authorizeInternalRelay`, which
reaches `validateInternalSignature`, which does `await request.clone().text()` to hash the
bytes. A Request whose body has been consumed cannot be cloned:

```
$ node --input-type=module -e "const r=new Request('https://x/p',{method:'POST',body:'{}'}); await r.text(); try{r.clone()}catch(e){console.log(e.constructor.name,'-',e.message)}"
TypeError - unusable
```

So every correctly signed first-party relay call would have thrown and 500'd. Changed to
`await request.clone().text()` and added two signed-path tests. Verified red-before-fix by
swapping just that line back:

```
× accepts a v2-signed delivery event on /api/v1/email/webhook
 Tests  1 failed | 19 skipped
```

### 13. `logEnd` was a no-op called from twelve request paths

`src/index.ts` L276. Now persists a `request_completed` event through `ctx.waitUntil`, so it
never delays the response. The twelve call sites are unchanged.

## Not done / carried forward

- **Not deployed.** Merging does not deploy. `npx wrangler deploy` still needs the real
  `STATUS_KV` / `HITL_KV` namespace ids, and two live routes changed shape:
  `/api/v1/email/inbound` and `/api/v1/email/webhook` now 401 unsigned callers, so the
  EmailIt webhook must be pointed at a signing secret before this ships.
- **`REPLACE_WITH_…_NAMESPACE_ID` will fail a real deploy on purpose.** That is the point —
  better to refuse than to ship a worker whose KV reads throw. Create the namespaces and
  substitute before the next deploy.
- **`POST /api/v1/dlq/validate`** is still unauthenticated. It only validates a shape and
  writes nothing, so it is a DoS surface rather than a data-integrity one; next run.
- **`POST /api/v1/kb/search`** is unauthenticated by design for the public site, but it
  embeds the query and calls the AI failover chain — worth a rate limit.
- **`GET /metrics`** is unauthenticated and unrated; it exposes queue depth and error counts.
- **`/api/v1/chat/upload-auth` signs uploads into bucket `support-attachments`**, while the
  only bucket migration in the repo creates `ticket_attachments`. One of the two names is
  wrong and uploads will 404. Not changed today because it needs a decision on which name is
  canonical in production.
- **`reprocessIntakePayload`** is still a stub returning `{ success: true }`.
- **`handleStaleTicketSweep` writes events but does not notify anyone.** Wiring it into
  `handleSLASweep`'s escalation path is the next step, otherwise the sweep is observable only
  in `events_ax2024`.
- **Still no `robot_fault_logs` table.** The mission brief refers to
  `public.robot_fault_logs`; no migration creates it and no code references it.
  `/api/v1/robotics/fault-ingest` writes the flight recorder payload into
  `support_tickets.metadata.flight_recorder_data` instead. `OnyxInvestigationPanel.jsx`
  renders robotics only when `ticket_ai_telemetry.category === 'Robotics / Hardware Fault'`,
  and never reads `metadata.flight_recorder_data` — so the telemetry is stored and never
  shown.
- **`logErr` still only console.errors**; it never persists to `events_ax2024`.
- **The self-fulfilling tests flagged in Phase 159** (`telemetry.test.js`, `health.test.js`,
  `command.test.js`, parts of `metrics.test.js`) are unchanged.
