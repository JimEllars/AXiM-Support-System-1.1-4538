## Defects found and fixed

### 1. Frontend test gate: the 60s worker-start window, not the tests

`npx vitest run` reported two files as `Failed to start forks worker`. Both files pass when
they start. The gate is not measuring test outcomes; it is measuring fork boot time, and
Phase 161's `maxWorkers: 2` only capped the contention instead of removing it.

Measured on this box:

```
import happy-dom ms: 20721      # 14 MB across 609 ESM files
new Window() ms: 245
```

A fork reports "started" only after its test environment module is imported, and
`START_TIMEOUT = 6e4` in `vitest/dist/chunks/cli-api` is hard-coded. Two forks importing a
609-file module graph at once blew it.

**Fix** — `vite.config.js` L29–L46: `fileParallelism: false` replaces `maxWorkers/minWorkers`.
There are five files and 24 tests; cross-file parallelism saves seconds of test time and
costs a 60s startup race.

### 2. `onyx-edge-worker`'s `npm test` ran vitest in watch mode

`onyx-edge-worker/package.json` L22: `"test": "vitest"`. `npm test` therefore never exits, and
the root `test:worker` script (`npm run test --prefix onyx-edge-worker`) inherited the same
hang. Now `vitest run`.

### 3. Four tables were written by the Worker but created by no migration

`support_tickets.metadata`, `support_tickets.resolved_at`, `support_tickets.category` and
`hitl_audit_logs.metadata` appear in fifteen write paths in `src/index.ts` and in zero
migrations. Each miss failed a statement whose error the caller discarded:

| Missing column | Call site | Observed effect |
|---|---|---|
| `support_tickets.metadata` | `handleSLASweep` L722 | the `sla_breached` guard could never be persisted, so the breach email and internal note repeated **every 15 minutes per breached ticket** |
| `support_tickets.metadata` | `robotics/fault-ingest` L3900+ | the fault ticket insert failed, so ingested robotics faults never produced a ticket for `OnyxInvestigationPanel.jsx` to render |
| `support_tickets.resolved_at` | `resolve-from-coder` | ticket update failed → `Failed to update ticket` 500 back to the Coding Lab, i.e. the DLQ fault the runbook describes |
| `hitl_audit_logs.metadata` | executive email bridge L2467 | update failed → `updatedHitl` null → no audit note, no directive |
| `support_tickets.category` | `robotics/fault-ingest` | same insert failure as above |
| `product_feedback.sentiment`, `.customer_email` | `handleCSATFeedback` | CSAT insert failed with 500 `DATABASE_ERROR` |

`20261401000000_ingress_performance_indexes.sql` already builds an index on
`metadata->>'chatbase_conversation_id'`, so that migration could never have applied either.

**Fix** — new `supabase/migrations/20261601000000_worker_written_columns.sql`, all
`ADD COLUMN IF NOT EXISTS`.

### 4. Every `events_ax2024` query filtered on a column that does not exist

`events_ax2024` has `created_at` (`20260512000000_events_schema.sql` L3–L6). Thirteen queries
in the Worker filtered, sorted or selected `timestamp`. Supabase returns an error and a null
`data`, and every caller treated that as "no rows":

| Call site | Symptom |
|---|---|
| `sendDailySystemProgressReport` (3 counts) | the executive digest reported 0 autonomous escalations, curations and resolutions, every night |
| `/api/v1/health/*` diagnostics (4 sites) | `last_executed` always null → `pending_initial_run` forever |
| `/api/v1/health/cron` | cron health never `healthy` |
| DLQ list (L3157) | the DLQ panel was always empty |
| `handleLeaderboardAnalytics` | memory renewals always 0 |

**Fix** — `src/index.ts`: all thirteen column references are now `created_at`. Verified with
`grep -n '"timestamp"'` returning nothing.

### 5. `handleSLASweep` had two passes over the same rows, one unguarded

`src/index.ts` L667–L790. The first pass (`breachedTickets`) escalated and noted on every run
with no idempotency check. The second (`activelyBreachedTickets`) carried the
`metadata.sla_breached` guard that defect 3 made ineffective. Both set `priority = 'urgent'`,
so the first ticket in a run was escalated, noted and emailed twice.

The first pass also looked up the department's leads, then used them only as a parameter in
the audit event — `notified_leads` named people who were never emailed — while the actual
email went to a hard-coded address.

**Fix** — one pass, one guard, one note, one email:

- skip when `metadata.sla_breached === true`;
- persist `sla_breached` / `sla_breached_at` / `sla_escalated_to` before writing anything
  else, and `continue` when that update fails (a failed guard write is exactly what produced
  the infinite note loop);
- send the breach email to the department's leads with the operator as fallback, and record
  the same list in the event, so `notified_leads` is true.

### 6. The 1-hour SLA warning required both email providers

`src/index.ts` L792: `if (env.EMAILIT_API_KEY && env.RESEND_API_KEY)`. `EmailDispatchManager`
is a failover chain; requiring both keys means an installation with one provider sends no
warning at all. Now `||`, and the dispatch manager is built once per sweep instead of per
ticket.

### 7. `handleStaleTicketSweep` wrote an event nothing consumed

Phase 160 made it insert `ticket_stale_sweep` events. No code reads that type, so a ticket
could go stale indefinitely while the sweep reported success.

**Fix** — `handleStaleTicketSweep` L391–L482 now escalates inline: priority lifted to at least
`high`, one internal note, one audit event, guarded by `metadata.stale_escalated_at` so a
ticket that stays stale does not accumulate 96 notes a day.

### 8. The Coding Lab patch callback wrote a status the enum does not contain

`POST /api/v1/tickets/:id/coder-patch` sets `status: "Review-Patch-Pending"` (L3366) and
`SLABadge.jsx` renders a dedicated badge for it, but `ticket_status` is
`('open','pending','resolved','closed')`. The update raised
`invalid input value for enum ticket_status`, so the interlock failed at its first step.

**Fix** — the enum value is added in `20261601000000_worker_written_columns.sql`. The code and
the UI already agreed on the name; the database did not.

### 9. `resolve-from-coder` ignored the status it was given

`const { status: ticketStatus, ... } = payload` then `.update({ status: 'resolved' })`. A
Coding Lab run that finished and closed the ticket left it in the open queue. It now honours
`resolved` / `closed` and falls back to `resolved` for anything else, sets `updated_at`, and
returns the effective status.

### 10. Two intake paths inserted non-UUIDs into UUID columns

| Call site | Column | Value | Result |
|---|---|---|---|
| Chatbase bridge L8525 | `customer_id` | the caller's email address | 22P02 → the bridge 500'd on the first message of **every new conversation** |
| Chatbase bridge L8526 | `organization_id` | the literal `"default"` | 22P02, same statement |
| Direct ingest L5155 | `customer_id` | the caller's email address | 22P02 → `Failed to insert ticket into database` |

**Fix** — `resolveCustomerId()` resolves the address against `contacts_ax2024` and returns
`null` when there is no contact (the email is preserved in `metadata.customer_email`), and
`uuidOrNull()` drops any tenant value that is not a UUID.

### 11. CSAT was 404 on read and 500 on write; the leaderboard scored nobody

- `handleCSATFeedback` selected `assigned_to` from `support_tickets` — the column is
  `assignee_id` — so `.single()` errored and **every** submission returned
  `404 TICKET_NOT_FOUND`.
- Fixed that, the insert then failed: `product_feedback` has `comments`, not `comment`, and no
  `sentiment` / `customer_email` columns → `500 DATABASE_ERROR`.
- `handleLeaderboardAnalytics` queried `ticket_feedback`, a table no migration creates, so
  `feedbacks` was null and every operator scored `avg_csat: 0`, forfeiting the CSAT bonus.

**Fix** — correct column names, columns added by the new migration, and CSAT attributed to the
ticket's `assignee_id` through `product_feedback`.

### 12. Merging a duplicate erased the ticket's metadata

L3366 (pre-fix): `update({ status: "closed", metadata: { merge_target: primary_ticket_id } })`
replaces the whole JSONB document, so a merged duplicate lost its flight-recorder payload,
chatbase conversation id and SLA flags. Now read-modify-write.

### 13. `logErr` never persisted anything

Twelve request paths call `logErr`; it was `console.error` only, so a failed request left no
durable trace while `logEnd` did. It now writes a `request_error` event (message + stack)
through `ctx.waitUntil`.

### 14. `EmailDispatchManager` probed a provider it has no key for

With no EmailIt key, `send()` still called EmailIt with `Authorization: Bearer undefined`,
which 401s, trips the **module-scoped** breaker for five minutes, and makes every subsequent
message report a provider outage. `send()` now routes straight to Resend when the EmailIt key
is absent, and `sendViaResend` returns a clear failure instead of a second guaranteed 401 when
neither provider is configured.

### 15. CGI probe patterns were only matched against the query string

`src/index.ts` L1740: the `?-d` / `auto_prepend_file` / `disable_functions` list was applied to
`url.search` only, so the same payloads in the path (`/api/v1/auto_prepend_file=/etc/passwd`)
went straight through. The path and decoded path are now in the probe sources; three cases
added to the trust-boundary suite.

### 16. The security-health endpoint advertised a fail-closed gate as optional

`hmac_verification: hmacActive ? "enforced" : "optional"` (two sites). Phase 160 made those
webhooks fail closed, so a missing secret is a misconfiguration. Now `"misconfigured"`.

### 17. `escalate_breached_slas()` raised on every pg_cron run

`20260705000000_sla_escalation.sql` L27–L40 compares `priority != 'escalated'` (not a member
of `ticket_priority`) and updates `assigned_to` (the column is `assignee_id`). Both raise, so
the five-minute job has never escalated anything.

**Fix** — `20261601000001_fix_sla_escalation_function.sql` rewrites the function with valid SQL
and a `priority <> 'urgent'` guard so the database safety net and the Worker sweep cannot
double-note the same ticket.

### 18. Dead dependencies and a single 1.19 MB chunk

- `echarts` and `echarts-for-react` were dependencies with no import anywhere in `src/`;
  `SupportMetrics.jsx` uses `recharts`. `@questlabs/react-sdk` was already unused after Phase
  161 removed its stylesheet. Removed: `package-lock.json` −1,421 lines.
- Every page was imported statically in `App.jsx`, so `/login` and the public `/submit` form
  downloaded the operator HUD, `recharts` and the 28 kB chat panel before first paint.

**Fix** — `React.lazy()` + one `Suspense` boundary for all five routes:

| Chunk | Before | After |
|---|---|---|
| entry `index-*.js` | **1,185.52 kB** (gzip 341.73) | **700.09 kB** (gzip 207.12) |
| `Dashboard-*.js` | — | 395.58 kB (gzip 114.13) |
| `TicketDetail-*.js` | — | 53.22 kB (gzip 13.81) |
| `PublicIntake-*.js` | — | 19.61 kB (gzip 5.99) |
| `MemoryHub-*.js` | — | 11.69 kB (gzip 3.62) |
| `Login-*.js` | — | 3.90 kB (gzip 1.43) |
| CSS | 82.70 kB (gzip 12.83) | 82.70 kB (gzip 12.83) |

A visitor on `/submit` now fetches 720 kB instead of 1,186 kB, and no analytics or chat code.

## Environment note (honest caveat, not a repo defect)

This sandbox exports `NODE_ENV=production`. `npm ci` honours that by omitting
devDependencies, which removed `vitest`, `vite`, `globals` and the `node_modules/.bin` links
mid-session and cost roughly an hour of install churn. The repo's lockfile was verified
coherent afterwards — `npm ci --include=dev --prefer-offline` completes with
`added 577 packages in 10m` and every gate above was run on that tree. CI does not set
`NODE_ENV`, so it is unaffected; the note exists so the next run does not misread the
symptom as a lockfile fault.

Cold-module-load latency here is also extreme (~30–50 ms per file: `import('happy-dom')`
alone is 21s). That is why the frontend suite is measured twice — `fileParallelism: false`
removes cross-fork contention, but a first run against a cold vite cache can still exceed
vitest's hard-coded 60s fork-start window on this filesystem. Warm runs are 86–123s.
