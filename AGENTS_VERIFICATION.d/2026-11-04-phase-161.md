## Defects found and fixed

### 1. Tailwind never ran in production builds — the app shipped unstyled

`vite.config.js` carried:

```js
css: {
  postcss: {
    plugins: []
  }
}
```

Supplying `css.postcss.plugins` replaces Vite's `postcss.config.js` lookup. `postcss.config.js`
is where `tailwindcss` and `autoprefixer` are registered, so both were skipped and the built
stylesheet was the source file verbatim:

```
@tailwind base;@tailwind components;@tailwind utilities;@layer base{body{@apply bg-axim-slate ...
```

0.78 kB of CSS, with `@tailwind`/`@apply` never expanded. This survived because a 2.03 MB
vendor stylesheet (defect 2) made the CSS total look plausible to anyone who only checked
the byte count.

**Fix:** deleted the `css` override so `postcss.config.js` runs. Verified with `postcss([tailwindcss(...)])`
directly (73,511 bytes of output) before rebuilding.

### 2. A 2.03 MB unused stylesheet was in the critical path

`src/App.jsx` imported `@questlabs/react-sdk/dist/style.css`. No file in `src/` renders a
Quest/HelpHub component — the import was the SDK's entire stylesheet, 1.56 MB of which is a
single base64 PNG for `.question-input-cont` plus a 200 kB `.tour-helper-button` rule.

**Fix:** removed the import. `@questlabs/react-sdk` stays in `package.json` for now; it is
referenced nowhere else, and dropping the dependency is a lockfile change that belongs with
the next Dependabot sweep.

### 3. Frontend test run was red on a 2 vCPU box

vitest hard-codes a 60s wait for a forked worker to report `started`
(`START_TIMEOUT = 6e4` in `vitest/dist/chunks/cli-api`). Each fork boots its own module graph
— `react-dom`, `@testing-library/react`, `happy-dom` — which is ~35s per fork here. The fork
count derives from the CPU count, so four files could be dispatched at once and the last one
missed the deadline.

**Fix, part one:** the wildcard `import * as FiIcons from 'react-icons/fi'` (defect 4) was
inflating every fork's graph. Replacing it dropped the suite from 146s to 86s and it went
green on its own.

**Fix, part two:** `vite.config.js` now pins `maxWorkers: 2` / `minWorkers: 1` so a busy
runner cannot re-create the contention. This is a ceiling, not a serial run.

### 4. `import * as FiIcons` defeated tree-shaking in seven components

`SafeIcon` read the barrel through a computed key (`FiIcons[`Fi${name}`]`), which rollup
cannot tree-shake, so every Feather icon shipped. Three files (`Sidebar.jsx`,
`CreateTicketModal.jsx`, `BatchTriageModal.jsx`) imported the barrel and only destructured
from it; the rest used `FiIcons.FiX`.

**Fix:** `SafeIcon` now resolves the six names it is actually called with (`Activity`, `Clock`,
`Shield`, `Terminal`, `CornerDownLeft`, `AlertTriangle`) from an explicit registry, and every
consumer imports icons by name. `FiAlertTriangle` remains the fallback for an unknown name.

### 5. Three components built worker URLs from a template literal

`TicketList.jsx`, `Customer360.jsx` and `RCADocumentBlock.jsx` each declared:

```js
const getEdgeWorkerUrl = () => {
    return import.meta.env.VITE_EDGE_WORKER_URL || "${workerUrl}";
};
```

`"${workerUrl}"` is a literal string, not interpolation — a build without
`VITE_EDGE_WORKER_URL` produced requests to `${workerUrl}/api/v1/...`, which cannot resolve.
Every other component already imports the shared helper.

**Fix:** all three import `getEdgeWorkerUrl` from `src/lib/edgeWorkerUrl.js`, which also
applies the `.replace(/\/+$/, '')` normalisation and the localhost fallback.

### 6. Rate-limit counters were shared across every route

`checkRateLimit` wrote `ratelimit:${ip}`. Two routes with different budgets therefore shared
one counter and one window: a client hitting the 10/min path twice and the 5/min intake path
four times was throttled on intake, and whichever route wrote last decided when the window
expired.

**Fix:** `checkRateLimit(ip, maxRequests, env, windowMs, bucket)` writes
`ratelimit:${bucket}:${ip}`. The three existing `handlePublicWebIngress` call sites pass
`'ingress'`.

### 7. Three read surfaces had no budget at all

- `GET /metrics` — queue depth and error counts, plus an R2 `list()` per call.
- `POST /api/v1/kb/search` — embeds the caller's text through Workers AI, then falls back to
  an `ilike` scan over `knowledge_articles`. Anonymous AI spend.
- `POST /api/v1/dlq/validate` — JSON parsing and schema work per call.

**Fix:** `enforceReadRateLimit()` with `READ_SURFACE_LIMITS = { metrics: 60, kbSearch: 20, dlqValidate: 20 }`,
returning `429` with `Retry-After: 60` and the bucket name. Missing `IDEMPOTENCY_KV` still
fails open, matching the existing helper's contract.

### 8. The Robotics flight recorder HUD rendered hard-coded fiction

`/api/v1/robotics/fault-ingest` stores the payload at
`support_tickets.metadata.flight_recorder_data`. `OnyxInvestigationPanel.jsx` never read it:

```jsx
<div>Pitch/Roll Attitude: <span className="text-red-400">DIVERGENCE DETECTED</span></div>
<div>Servo Thermal: <span className="text-orange-400">ELEVATED</span></div>
<div>E-Stop Triggered: <span className="text-zinc-500">YES</span></div>
```

Any ticket whose telemetry category was `Robotics / Hardware Fault` showed those three
claims regardless of what the machine reported — fabricated diagnostics on urgent hardware
tickets.

**Fix:** the panel loads `support_tickets.metadata` alongside the telemetry row, renders the
scalar readings it actually received (escaped through `sanitizePayload`), shows the node id,
and states plainly when no flight recorder payload was ingested. Robotics detection now also
keys off `metadata.is_robotics` and the presence of recorder data, because
`fault-ingest` writes neither a `ticket_ai_telemetry` row nor its category.
